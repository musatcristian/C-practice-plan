Firmware learning path: granular plan, weeks 4 to 34

Cristian Musat · exact exercises, per-week pass/fail tests, document sections to read · 4 November 2026

Assumptions and reading key

Board assumption. An STM32 Nucleo-64 class board with a Cortex-M4 (for example a NUCLEO-F411RE) or Cortex-M7. If you choose a different family, every ST document reference below is replaced by the equivalent for your part; the section names stay the same, which is why they are given as names. A Zephyr-supported board is strongly preferred, because Phase 6 loses a week otherwise.

KeyDocument (all free from the vendor unless marked)
DATASHEETYour part's datasheet. The sections you need are "Features", "Memory mapping" and, later, pin and alternate-function tables.
RMYour part family's Reference Manual (for F4: RM0090). Sections are named identically across families: "Memory and bus architecture", "RCC", "GPIO", "EXTI", "NVIC", "USART", "SPI", "I2C", "bxCAN"/"FDCAN", "Independent watchdog", "Debug support".
PM0214STM32 Cortex-M4 MCUs and MPUs programming manual. Chapters: processor modes and privilege, exceptions and the vector table, fault handling, SysTick, DWT, SCB registers.
DDI0403EARMv7-M Architecture Reference Manual. Chapter B1 (system level architecture, memory map, exceptions), B3 (fault handling), C1 (debug).
DUI0555Cortex-M4 Devices Generic User Guide: NVIC, SysTick, SCB, DWT, ITM register descriptions.
UM1724STM32 Nucleo-64 boards user manual: jumper configuration, ST-LINK, virtual COM port wiring.
LDGNU ld manual, "Linker Scripts" chapter, plus readelf and objdump sections of the binutils manual.
ZEPHYRZephyr documentation: Getting Started, "Build with west", Devicetree guide, Kconfig guide, Kernel Services, Board Porting Guide, Memory Management, Thread Analyzer.
FREERTOSMastering the FreeRTOS Real Time Kernel (free PDF): chapters on task management, queues, semaphores and mutexes, and priority inversion.
LIULiu and Layland, "Scheduling Algorithms for Multiprogramming in a Hard-Real-Time Environment" (1973). Short paper, read it twice.
BUTTAZZOHard Real-Time Computing Systems, chapters on fixed-priority scheduling and response-time analysis.
UM10204NXP I2C-bus specification and user manual: START/STOP conditions, addressing, clock stretching, arbitration.
CANBosch CAN 2.0B specification (free). ISO 11898-1 is the normative standard but is paywalled; say so in your notes rather than pretending to have read it.
KERNELkernel.org documentation: driver-api, "Locking", "Unreliable Guide to Locking", "Submitting patches", "Coding style", KCSAN, plus Linux Device Drivers 3rd ed. (free) chapters 2, 3 and 5.
CERT/MISRASEI CERT C Coding Standard (relevant rules named per week) and MISRA C:2012 (paywalled; the directive and rule numbers are enough for practice).

Rule that governs every week. An exercise is not done until its acceptance test passes and the evidence is committed. If you complete the exercises but the test fails, the week is not finished and you do not move on.

Phase 4 · Weeks 4 to 7 · Production C

WeekExact exercisesAcceptance test (pass/fail)
4 Exercises
  1. Rebuild your weeks 1 to 3 code with -std=c11 -Wall -Wextra -Werror -Wconversion -Wshadow -Wcast-qual -Wstrict-prototypes -Wmissing-prototypes -Wundef -Wdouble-promotion.
  2. Fix every diagnostic. You may lower a flag, but only with a committed one-line justification naming the reason.
  3. Add clang-tidy with the bugprone-*, cert-* and readability-* families, and fix what it finds.
  4. Write a Makefile with all, check, clean targets, and a .gitignore that excludes build output.
Read GCC "Warning Options" chapter; clang-tidy checks reference (the families you enabled); CERT C rules INT30-34, MEM30-33 as an index of what is coming.		 From a fresh clone on a machine that has never built the project, make check exits 0 with zero warnings. The count of suppressed checks is three or fewer, each justified.
5 Exercises
  1. Refactor the sensor registry into a library with an opaque handle: sensor_registry_create, _destroy, _add, _find, _list.
  2. Replace every exit() and assert() in library code with returned error codes from a single enum.
  3. Write a test harness (Unity, or 60 lines of your own) with at least one test per public function and one test per failure path, using a function-pointer allocator so you can inject malloc failure.
  4. Add an examples/ program that uses only the public header.
Read Jens Gustedt, Modern C, chapters on interfaces, linkage and opaque types; CERT C DCL and MEM rules; Linux kernel coding-style document for naming and error-handling conventions (as reference, not gospel).		 make test from clean passes. Every public function has a failure-path test. grep -rn "exit(\|assert(" lib/ include/ returns nothing. The examples program compiles against the public header only.
6 Exercises
  1. Build three variants: -fsanitize=address, -fsanitize=undefined, and both together. Run the full test suite under each.
  2. Write a libFuzzer harness for the input parser. Run it for a total of at least 10 minutes of wall clock.
  3. For every crash found: minimise the input, commit it as a regression test, and show the test failing before the fix and passing after.
Read libFuzzer documentation (llvm.org/docs/LibFuzzer); AddressSanitizer and UBSan reference pages; GCC instrumentation options; CERT C MEM30-31.		 At least one genuine crash found by fuzzing, with a four-line evidence block committed: the minimised input, the pre-fix output, the fix, the post-fix output. A suite that passes only because it never exercises the parser is a fail.
7 Exercises
  1. Pick a real issue in Zephyr or an embedded utility library. Start from labelled good-first issues; fix; submit a PR following their contribution rules.
  2. Ask one colleague at work to review your registry and give you written feedback. Do not defend, just record.
  3. Write REVIEW.md: what reviewers said, what you changed, what you disagreed with and why.
Read Zephyr CONTRIBUTING.rst and commit-message guidelines; the subsystem maintainer's review comments, carefully.		 One PR merged or reviewed with substantive comments, plus REVIEW.md containing at least three pieces of external feedback you acted on. No PR and no review means the week repeats.

Phase 5 · Weeks 8 to 11 · Bare-metal bring-up

WeekExact exercisesAcceptance test (pass/fail)
8 Exercises
  1. From DATASHEET "Memory mapping", write down flash origin, size, RAM origin, size by hand before touching the toolchain.
  2. Write the linker script yourself: MEMORY with FLASH and RAM, ENTRY(Reset_Handler), _estack at top of RAM, and SECTIONS placing .isr_vector, .text, .rodata, .data with separate LMA in flash and VMA in RAM, ._user_heap_stack, and .bss with NOLOAD.
  3. Symbols _sidata, _sdata, _edata, _sbss, _ebss. Build with -Map=build/firmware.map.
  4. Inspect with readelf -S, readelf -l, objdump -h, and read the map file.
Read LD "Linker Scripts" (MEMORY, SECTIONS, VMA/LMA, AT>, NOLOAD, KEEP); DATASHEET "Memory mapping"; RM "Memory and bus architecture"; DDI0403E B1.4 (memory map and the initial vector table address).		 Three committed proofs: (a) readelf -S showing sections at the datasheet addresses; (b) readelf -l showing .data with a load address in flash and a different virtual address in RAM; (c) a NOTES.md paragraph explaining, in your words, why .data needs two addresses and .bss needs none.
9 Exercises
  1. Write startup.c (or .s) with Reset_Handler: copy from _sidata to _sdata.._edata, zero _sbss.._ebss, call main, and an infinite loop if main returns.
  2. Weak default handlers for every exception, all aliasing a Default_Handler that loops.
  3. Make main prove it ran: toggle a GPIO at register level, or write one character with a register-level polled UART.
Read PM0214 chapter "Exceptions" (vector table layout, stacking, the initial SP/PC fetch); DDI0403E B1.5; RM "GPIO" register descriptions and "RCC" AHB/APB enable registers; UM1724 for the LED pin and the virtual COM port pins.		 Board visibly blinks or transmits with no HAL and no IDE project file. Disassembly (objdump -d) shows the copy loop reading _sidata. readelf word 0 of .isr_vector equals _estack and word 1 equals Reset_Handler.
10 Exercises
  1. Enable the GPIO clock via the RCC register, set MODER/OTYPER/OSPEEDR/PUPDR, and toggle.
  2. Configure SysTick for a 1 ms tick and toggle an LED from the handler at exactly 1 Hz. Then do the same with a different peripheral's EXTI line and a button.
  3. Enable the interrupt in the NVIC with an explicit priority. Change the priority and record what changes.
  4. For every register you touch, cite the register field name from RM in a comment.
Read RM "RCC" (enable registers, clock tree), "GPIO" (all register descriptions), "EXTI", "NVIC"; PM0214 SysTick chapter; DUI0555 NVIC and SysTick register descriptions.		 LED toggles at 1 Hz from the interrupt with main in an empty loop. A committed register table: register, field, value, and the RM section it came from. Anyone reading it can reproduce the configuration without your code.
11 Exercises
  1. Induce three distinct faults: a write through a null pointer, an unaligned access through a packed-struct pointer, and an invalid instruction via a bad function pointer.
  2. Write HardFault_Handler in C that reads the stacked frame (r0-r3, r12, lr, pc, xPSR) and either transmits it or latches it to a known RAM address you inspect in the debugger.
  3. Decode CFSR, HFSR, MMFAR and BFAR for each fault and map the stacked PC back to a source line with addr2line -e build/firmware.elf.
Read PM0214 fault-handling chapter and the SCB register descriptions; DDI0403E B3.2 (fault types and escalation); Joseph Yiu, Definitive Guide to Cortex-M, fault-handling chapter.		 A committed table with one row per fault: fault type, CFSR bit set, stacked PC, addr2line file:line, and your one-sentence explanation. Three faults, three correctly identified source lines.

Phase 6 · Weeks 12 to 17 · RTOS and timing

WeekExact exercisesAcceptance test (pass/fail)
12 Exercises
  1. Install the Zephyr SDK and west; build and flash hello_world for your board.
  2. Build blinky and change it to a different LED through the devicetree alias only, touching no C.
  3. Read build/zephyr/zephyr.dts and locate your board's .dts in the tree. Diff it against the generated one.
  4. Write BRINGUP.md comparing your Phase 5 startup code against Zephyr's port: who provides the vector table, who sets the stack, where main is called from.
Read ZEPHYR Getting Started; "Build with west"; Devicetree guide (bindings, aliases, overlays); Kconfig guide; Board Porting Guide.		 Two applications running on the board. BRINGUP.md answers all three questions correctly and names the file in Zephyr where the C runtime init happens.
13 Exercises
  1. Three threads at priorities 2, 5 and 8. High-priority sleeps on a semaphore; low-priority holds a resource.
  2. Create a genuine priority inversion with a k_sem used as a lock, and measure it.
  3. Fix it with k_mutex (priority inheritance) and measure again.
  4. Add an ISR that posts to a k_msgq consumed by a thread. Explain why the queue is safe and a bare global is not.
Read ZEPHYR Kernel Services: threads, scheduling, synchronization, data passing, interrupts; FREERTOS chapters on queues and mutexes (for the contrasting API and the inversion discussion).		 Two measured numbers for the same scenario, before and after the mutex, with the mechanism explained. A queue-based ISR handoff that works, plus one paragraph on why the global-variable version is undefined behaviour.
14 Exercises (Gate week)
  1. Instrument: GPIO high at ISR entry, low at ISR exit; GPIO high at task wake, low at task completion. Capture at least 1000 transitions on the logic analyser.
  2. Cross-check in code using DWT->CYCCNT with CoreDebug->DEMCR trace enable, converting cycles to microseconds.
  3. Repeat under load: add a low-priority busy thread and a higher-rate interrupt, then report both distributions.
  4. Write LATENCY.md: deadline, method, N, worst case, median, jitter, and the conditions under which the number is valid.
Read PM0214 DWT chapter; DDI0403E C1 (debug and trace); DUI0555 DWT and DEMCR; Zephyr timing and k_cycle_get_32 documentation.		 Gate 1. LATENCY.md exists with a defensible worst case and a stated method. Both measurement approaches agree within a factor you can explain. If you cannot produce this, stop the plan and keep the full stack base.
15 Exercises
  1. Compute total utilisation for your task set. Compute the rate-monotonic bound for n tasks and compare.
  2. Do a response-time analysis per task, accounting for blocking and ISR interference.
  3. State every assumption (zero overhead, no cache effects, no priority inversion) and say which ones your measurements contradict.
Read LIU (whole paper); BUTTAZZO fixed-priority scheduling and response-time analysis chapters.		 A written analysis with a clear conclusion. "Not provably schedulable, and here is the observed margin" is an acceptable and honest answer. "Schedulable" with no arithmetic shown is not.
16 Exercises
  1. Remove all dynamic allocation. Configure fixed-size pools or static buffers. Disable the Zephyr heap (CONFIG_HEAP_MEM_POOL_SIZE=0).
  2. Measure per-thread stack high-water marks with the thread analyzer, and with a fill-pattern (0xA5) method as a cross-check.
  3. Resize stacks with at least 25 percent margin and justify the number.
Read ZEPHYR Memory Management and Thread Analyzer; CERT C rules on dynamic memory (MEM30-33) and MISRA C Directive 4.12 (dynamic memory shall not be used).		 Zero dynamic allocation, proven by grep and by the heap configuration. A stack table: thread, high-water mark, allocated, margin. All margins at or above 25 percent.
17 Exercises
  1. Add an independent watchdog with a defined refresh policy and reset-cause capture at boot.
  2. Deliberately hang a thread and prove recovery, recording the reset count.
  3. Run clang-tidy with MISRA-adjacent checks over the firmware and justify every deviation.
  4. Add defensive validation to every externally sourced input.
Read RM "Independent watchdog"; Zephyr watchdog API; MISRA C:2012 Dir 4.1, 4.7 and Rules 17.7, 21.3 (the ones you will actually violate).		 Watchdog demonstrably recovers from a hang, evidenced by a reset count and a boot log. Zero unjustified MISRA deviations. Every parser entry point rejects at least one malformed input in a test.

Gate 1 · end of week 14. Pass: a measured worst-case ISR-to-task latency with a stated method, and you found the work absorbing. Stop: no measurement exists, or you did not enjoy it. Do not buy the Linux board.

Phase 7 · Weeks 18 to 20 · Protocols at the wire

WeekExact exercisesAcceptance test (pass/fail)
18 Exercises
  1. Pick one real I2C sensor and one real SPI device. Read the register map from the datasheet and write the identification-read as your first transaction.
  2. Implement the init sequence and read a measurement, both from scratch, then again through the RTOS driver model.
  3. Decode both buses on the logic analyser: addresses, ACK/NACK, clock stretching on I2C, mode and bit order on SPI.
  4. Draw your captured timing next to the datasheet's timing diagram and annotate the differences.
Read UM10204 sections on START/STOP, addressing, ACK, clock stretching, arbitration; your sensor datasheet's register map and timing table; RM "I2C" and "SPI" chapters; the device's datasheet timing characteristics.		 Two decoded captures committed, each with an annotated timing comparison against the datasheet. A byte-level commentary: what each byte means. A capture you cannot explain is a fail.
19 Exercises
  1. Compute bit timing by hand for your target bitrate from APB clock, prescaler, BS1, BS2 and SJW, and verify on the analyser.
  2. Send and receive between two nodes, or loopback with a simulated peer. Configure acceptance filters and prove a filtered frame is dropped.
  3. Force an error state and observe error counters incrementing toward bus-off, then recover.
  4. Write one page on how CAN FD differs and why automotive is moving to it.
Read Bosch CAN 2.0B specification (framing, arbitration, error handling, fault confinement); RM "bxCAN"/"FDCAN" chapter; note in your write-up that ISO 11898-1 is paywalled and that you worked from the Bosch spec.		 Captured frames with correct bit timing verified against your hand calculation. Evidence of a filter dropping a frame. A bus-off occurred and recovered, with the counter values recorded.
20 Exercises
  1. Build an image with Yocto or Buildroot for a supported board. Add either a layer with a recipe or a Buildroot package.
  2. Write a devicetree overlay from scratch that enables a node and sets a property.
  3. Verify on the target in /proc/device-tree, and diff your Linux devicetree approach against Zephyr's.
Read Yocto Project Overview and Concepts Manual plus the Dev Manual sections on layers, recipes and BSPs (or the Buildroot manual equivalent); devicetree-specification (readthedocs); kernel devicetree/usage-model doc.		 A reproducible image (same commit, same command, same result), booting, with your overlay node visible and its property readable. A pinned configuration file committed.

Phase 8 · Weeks 21 to 26 · Firmware to Linux boundary

WeekExact exercisesAcceptance test (pass/fail)
21 Exercises
  1. Write a loadable module: module_init/module_exit, alloc_chrdev_region, cdev_add, a file_operations with open/read/write/release, and copy_to_user/copy_from_user.
  2. Write a userspace program that exercises it. Handle every error path in the module and unwind correctly.
  3. Build out of tree against your board's kernel headers with a two-target Makefile.
Read KERNEL driver-api (char devices, ioctl); Linux Device Drivers 3rd ed. chapters 2 and 3; kernel coding-style.		 Insert, exercise, remove, and a clean dmesg with no warnings. Unload leaves no reserved major, no leaked memory (check with the kernel's own leak reporting if available).
22 Exercises
  1. Two threads sharing a buffer with no lock. Demonstrate the race, then detect it with KCSAN if your kernel supports it.
  2. Fix with a mutex, then a spinlock, and write down which is correct in which context and why.
  3. Move work out of interrupt context with a workqueue or a threaded IRQ handler.
Read KERNEL "Locking" and "Unreliable Guide to Locking"; KCSAN documentation; LDD3 chapter 5.		 A race reproduced at least once with evidence, a fix, and a written explanation of sleeping versus atomic context. The explanation must be correct about why a mutex cannot be used in an IRQ handler.
23 Exercises
  1. Find one real defect in a subsystem you actually touched. Run checkpatch.pl, sparse, and read the TODO files.
  2. Fix it and submit with git send-email following the subsystem's rules exactly.
  3. Respond to review. Record everything.
Read KERNEL "Submitting patches", "Coding style", MAINTAINERS, and your subsystem's own documentation file.		 One patch sent upstream. Reviewer feedback received and answered is a pass. A well-argued rejection is also a pass. A patch never sent is a fail.
24 Exercises
  1. Run on a PREEMPT_RT kernel and on a non-RT kernel. Run cyclictest -m -p95 -i200 -d for at least 15 minutes on each, under load.
  2. Interpret the maximum, not the average. Identify what dominates the tail on your board (SMI, power management, driver latency).
  3. Tune one thing (IRQ affinity or a threaded IRQ priority) and measure the effect.
Read kernel documentation on RT-mutex and PREEMPT_RT; rt-tests README and cyclictest man page; the PREEMPT_RT wiki page on configuration basics.		 Four distributions (RT and non-RT, idle and loaded) with max values, plus a written statement of what dominates the tail and what you changed to improve it. Average latency reported without a maximum is a fail.
25 Exercises
  1. Define a frame format: SOF, length, sequence, payload, CRC16. Write the specification first, before the code.
  2. Implement both ends: MCU firmware and Linux userspace.
  3. Inject errors: corrupt a byte, truncate a frame, duplicate one, send garbage. Handle each defined way.
  4. Capture the exchange on the analyser.
Read Your own specification (it is now a real document); a CRC reference for CRC-16/CCITT; the CERT rules on validating externally sourced data.		 Two devices exchanging frames, a specification document, a capture, and four error cases each handled and evidenced. This repository is the one you will show people.
26 Exercises
  1. Host-side unit tests for the protocol logic (parse and build, no hardware needed).
  2. A hardware-in-the-loop test script that runs the error cases automatically.
  3. CI on a clean runner building both halves.
Read Your CI provider's runner documentation for hardware you can attach, or design the HIL test to run only locally and gate the rest in CI.		 make verify from a clean clone passes end to end with no manual step, in CI, plus locally with hardware attached.

Gate 2 · end of week 26. Pass: you can explain a register-level or kernel-level bug you fixed, and make verify passes from clean. Not yet: repeat weeks 21 to 23 on a harder subsystem. Do not start positioning on a thin artefact.

Add a --version output captured into the repo for reproducibility. A machine that has never seen the project builds and flashes it by following the README only. You must actually test this on a second machine or a fresh container.

30 Exercises Write one technical post about a non-obvious bug or trade-off from the project. Publish it where engineers will read it. Published, and at least one substantive comment or question from an engineer who is not you.

Phase 10 · Weeks 31 to 34 · Positioning and decision

WeekExact exercisesAcceptance test (pass/fail)
31 Exercises Identify a named internal team with device, automotive, industrial or edge work. Write one page: their problems in their words, your evidence against each, and what you would need to learn on the job. The page is specific enough that it could not be sent to a different team unchanged. If it could, it is a fail and you rewrite it.
32 Exercises Talk to that team's lead first, showing the artefact. Then brief Ruben before any formal request. Ask for a six-month rotation or partial allocation, framed as depth transfer at current grade. A named team lead has seen the artefact and given a specific reaction. Your manager was briefed before the request became official.
33 Exercises Rehearse defending your latency measurement, your schedulability analysis, and one hardware bug at register level. Practise explaining the seam system in ten minutes. Ask an engineer to challenge you honestly. A rehearsal completed, plus a written list of the questions you could not answer confidently. That list is your revision plan, not a failure.
34 Exercises Decide: rotation secured, continue self-directed with a revised plan, or conclude that full stack plus systems awareness is the better position for now. Sketch the next twelve months either way. A written decision with the evidence that drove it and a next-twelve-months sketch. All three outcomes are valid; the failure mode is drifting into none of them.

Reading load, honestly

The reading in this plan is deliberately document-heavy and book-light. Reference manuals are the actual source of truth for firmware and nobody reads them end to end; you read the one chapter your register lives in, and you cite the section. Total book reading across 31 weeks is under 400 pages (Gustedt selectively, Yiu's fault chapter, the FreeRTOS kernel chapters, Buttazzo's two chapters, LDD3 chapters 2, 3 and 5, plus the Liu paper twice). Everything else is vendor documentation and standards, consulted per week.

What would make this plan wrong

  • Weeks 8 to 10 collapse if the board misbehaves. If the debug probe does not work, stop and fix that first; do not proceed to startup code with an unreliable flash path.
  • Week 23 depends on finding a real defect. If nothing surfaces, substitute a subsystem documentation improvement that a maintainer accepts. It is weaker evidence but still real.
  • Week 24 needs a board that can run a modern kernel. If your Linux board is too constrained for PREEMPT_RT work, run cyclictest on a VM or on your workstation and say so explicitly in the write-up rather than faking it.
  • The 6 to 8 hour week assumption. Weeks 14, 22, 24 and 26 are the heavy ones. If any single week exceeds 10 hours, cut its fourth exercise rather than the acceptance test.
